# 后台手机端对标分析与调整方案

日期：2026-09-28。代码基线：`c8bcbfd`，已推送 `codex/admin-legacy-theme`。

本轮仅检查、分析和编写方案，没有修改业务代码、响应式样式或服务器配置。

## 1. 检查范围与证据边界

- 参照网站：<https://453400.80909.cn/sys/dashboard>，已登录后逐一打开侧栏中的全部 17 个业务页面。
- 本地网站：`http://localhost:8080`，使用项目记录的本地初始化账号登录，逐一打开对应的 17 个业务页面；没有重置密码。
- 两边主检查视口为 375×667。参照返水页额外检查 390、414、767、768、1024px 宽度，等待布局动画结束后测量断点。
- 参照弹窗抽查：会员编辑、预设订单添加、手动结算、返水一键设置；本地抽查会员编辑。只打开、查看、取消，没有保存、审核、退码、派奖、清理或开关操作。
- 对照源代码：后台布局、两套全局样式、分页组件和各业务页面。
- 本地此次浏览器实际存在 `html.dark` 状态。这是本次实测环境的事实，不能推断所有用户都如此；但“暗色状态下旧后台主题被污染”需要纳入必测项。
- 桌面端仅做代表性断点检查，不宣称已完成所有桌面页的逐像素验收。真实 iOS/Android 软键盘、触摸和字体渲染仍需在实施后补验。
- 两边数据量、会员类型、金额、配置值和到期日期不同，不作为布局差异，也不复制参照账号的业务数据。参照菜单没有本项目的快捷指令、系统管理和基础设施，后者只能沿用设计规则，不能称为已与对应页面对比。

## 2. 结论

不能用“所有表格固定 720px”或“手机全部换卡片”实现对标。参照保留传统表格：普通列表自然压缩与换行，会员列表另有内部横向滚动。表单与弹窗则单列排列。

目前最明显的问题不只是字号：本地暗色变量、布局内外双重留白、全局隐藏标题、大列宽和弹窗层级共同影响画面。应先消除这些基础差异，再逐页校准，最后验收；业务权限、分页查询、轮询和资金逻辑不应跟着换界面而改动。

## 5. 可靠的实施顺序

### P0：固定主题与布局基础

1. 给旧后台建立明确的主题边界，补全背景、overlay、输入、选择器、导航等变量。覆盖后台范围内的暗色工具类影响，不能只改body的少数变量；进入房间/离开后台时不得污染其独立主题。
2. 检查 CSS 选择器与实际DOM类名，包括 `.v-collapse` 与现有 `.luck-collapse`。确保菜单、白色图标、到期文字、用户入口在手机和桌面都可见。
3. 移动壳采用参照的正常纵向页面滚动，消除内外双重padding；两层头部、品牌居中、230px侧栏与推移行为统一。
4. 统一后台主断点为 `max-width:767px`，768px回到桌面布局；具体表单和页面辅助断点仅在确有参照依据时保留。
5. 弹窗采用页面级遮罩和统一层级。遮罩必须覆盖头部；回到顶部、菜单和其他浮层不得压过弹窗或阻挡底部按钮。

### P1：统一列表的结构，不只是 CSS

当前 Element 表格的 `min-width` 列属性、内部colgroup与表头/表体/表尾分离，无法靠给外层 `width:100%` 解决。

建议建立一个只负责旧后台展示的共用表格适配层，沿用页面现有的数据与事件：

- 桌面先保持已确认的现有展示；手机普通列表使用原生语义表格 `table-layout:auto`、真实 `thead/tbody/tfoot`，使列能依内容自然压缩与换行。
- 同一份列定义负责标题、单元格插槽、对齐与表尾；只有一份数据源、分页状态和操作函数，不建立第二套请求或复制业务判断。
- 区分 `fluid` 普通列表、`dense` 密集返水、`member-scroll` 会员列表三种布局，而不是给全部列表720px下限。
- 会员的横向滚动只限定在表格容器中；操作行、表头和表尾保持正确对齐，筛选、统计和分页不能跟着横滚。
- 长文本允许换行，金额/期号/时间按页面规则处理；消息使用保留换行的左对齐文本，图片上限为单元格可用宽度。
- 若先继续用 Element 作为过渡，必须同步调整每列的手机宽度、表体和表尾，而非仅移除外层min-width；不能把这种过渡视为最终逐像素完成。

分页/工具条也要统一适配：

- 有条数选择的页面默认10条，参照选项10/25/50/100；并非每个页面都有条数选择，不能强行统一加上。
- 手机条数、搜索、记录数、分页按各页参照顺序排列；不要让搜索和顶部新增/清理按钮占满整行。
- 有数据/无数据都保留表尾；记录数正确，翻页禁用状态正确，分页按钮换行位置可达。
- `PaginatedTable` 只管客户端分页列表；独立服务端分页页继续使用自己的接口和总数，不能降级全量拉取后本地分页。

### P2：逐页表单、弹窗与视觉校准

1. 配置、额度、赔率页面统一手机标签上置、控件34px、输入左对齐。消除固定桌面190px输入宽度在手机仍生效的问题。
2. 小搜索按钮按内容宽，保存靠右。参照弹窗取消靠左、确定靠右，不沿用统一最小88px。
3. 表头与表尾共用字体、字号、内边距、边框和列宽；密集返水单独采用紧凑参数。
4. 恢复被隐藏的业务标题，统一主副标题自然换行。去掉不对应参照的额外padding和默认卡片间隔。
5. 图标列出逐项映射，按实际轮廓、大小、基线对照。只统一图标名或颜色不够；必要时使用现有可用FontAwesome兼容图标或代码原生SVG，不用字体字符拼凑。
6. 对标字体加载情况和中文fallback，不只声明font-family。所有比较使用同一系统、视口和缩放；不同操作系统的字形差异不能用整体缩放页面来掩盖。

### P3：全页验收后才发布

1. 先验证P0，再选“预设订单、会员、消息”三页试点，分别覆盖普通表、横滚操作行和长内容。
2. 试点通过后推广到全部17页，再校准表单与抽查弹窗。
3. 每一阶段只改对应组件/页面，不全量格式化或重排无关文件。
4. 修改完成后再构建部署和提交；此方案不代表已经达到“一模一样”。

## 6. 必须保留的业务与规范边界

- 不改用户/租户隔离、服务端退码归属和封盘守卫、资金流水、结算幂等、真实盘口写入或开奖时序。
- 不因外观一致删除本项目额外的安全确认、人工开奖原因、服务端分页与必要操作入口。
- 真实时间和金额来自我们自己的数据；仅调整格式，不能伪造为参照页面的时间或数值。
- 图形改动只在后台范围生效，不影响房间聊天、机器人头像、回执、刮牌、虚拟键盘和输入区。
- `AGENTS.md` 目前仍规定手机全部卡片、禁横滚，和此次实测目标及现有 `mobileCards=false` 不一致。正式实施时应同步更新成“按参照保留表格，会员允许受限内部横滚”，撤销矛盾的旧验收项；本轮没有更新规范。
- 参照操作记录表尾错序等明显问题不复制；已有“所有表尾与表头一样”的用户要求继续有效。
- 快捷指令、系统管理和基础设施无参照页面，使用共用主题规则，但不要强行删功能或宣称对标完全一致。

## 7. 验收清单

主矩阵：全部17页×375/390/414px；代表页面补320px、767/768px、1024px及常用桌面宽度。

- 同一视口、缩放与数据形态截图对照，检查顶部、标题、筛选、表格、表尾、分页和页底；长页面同时检查下半部，不只看首屏。
- 结构基准位置/高度目标误差≤2 CSS px；文字换行、列顺序、操作顺序与显隐一致。金额、日期、不同条数等动态区域从图像差异判定中单独排除。
- 375×667下所有主要业务字段和操作可读/可达；普通表不能依赖全局横滚，会员只在自己的表格中横滚。
- 页面 `scrollWidth <= clientWidth`，再逐个核对正文和容器边界，防止 `overflow:hidden` 只是把超宽内容裁掉。存在浏览器滚动条时不要求机械等于innerWidth。
- 每个表格检查空数据、少量数据、长昵称、长指令、长时间、大金额、负值和多页；仅在本地使用测试夹具，不能向参照网站造数据。
- 表头、表体、表尾横滚和调整窗口后仍对齐；每页条数变化后页码/统计正确，隐藏与可见表格不能保留两套分页状态。
- 弹窗检查会员、预设、手动开奖、返水设置、订单详情、清理确认；顶部/底部按钮在短屏、长内容和软键盘下仍可达，取消不产生业务写入。
- 检查新浏览器和已有暗色缓存两种状态，不出现黑底黑字、白底白图标或不可见导航文字。
- 检查手机菜单开关、页面切换、刷新和旋转；正常页面滚动与返回位置符合参照。
- 桌面回归不得破坏之前确认的页面；房间页面独立做聊天、回执、已退码状态、开奖结果、键盘和刮牌入口回归。
- 执行受影响文件lint、类型检查（先生成自动导入声明）和`pnpm build:docker`；UI操作仍使用本地Mock/老板模式，不拿真实盘口做写入测试。
